## Project notes

- **Test command:** `python -m unittest discover -s tests -t .` (from repo root). Tests use `unittest`, not pytest.
- **CI:** `.github/workflows/ci.yml` runs `ruff check .` and the test suite on every PR and push to `main`; the same commands are pinned in `.no-mistakes.yaml` (`commands.lint` is `uvx ruff check .` because `ruff` is not on the pipeline-host PATH, though `uvx` is). Use `python3`, not `python`: only `python3` is installed on the pipeline host (GitHub runners ship both).
- **Ruff pinning:** `pyproject.toml` pins `[tool.ruff.lint] select` to the stable pre-0.16 default (rationale in the comment there); widen it only together with fixing the resulting findings.
- **No third-party dependencies.** Stdlib only: `urllib`, `html.parser`, `sqlite3`, `tomllib`, `unittest`. Do not add a dependency without a strong reason; `pip install` is blocked in the dev environment anyway.
- **Read-only inputs** (never modify, paths come from `config.toml`): master profile `PROFILE.md`, style template `Abhigyan_Resume_AI_ML.tex`, and the LaTeX engine. The preamble of the style template is reused verbatim by `jobpilot/resume/generator.py`.
- **LaTeX engine is a Windows `.exe` run from WSL.** `jobpilot/resume/compiler.py` runs it with `cwd` set to the `.tex` directory and a relative filename so path translation works. `pdftotext.exe` ships in the same MiKTeX bin dir and powers the parseability check.
- **Any Windows `.exe` invoked from WSL must get a `cwd` + relative filename, never an absolute Linux path argument** (WSL does not translate those, so the process cannot open the file). Both `compiler.py` and `resume/parseability.py:extract_pdf_text` follow this; `tests/test_tailoring.py` guards the extractor invocation without needing the toolchain. The integration test `test_tailored_resume_compiles_and_is_parseable` is the end-to-end check.
- **The LaTeX engine's stdout/stderr is not guaranteed UTF-8.** `compiler.py` runs `subprocess.run(..., text=True, encoding="utf-8", errors="replace")`, so a `.tex` containing non-ASCII text no longer raises `UnicodeDecodeError` (gap G3 in `data/jobpilot-run-07/report.md`). Tolerant decoding alone is not enough: pdflatex cannot typeset non-Latin scripts, so `cover_letter.py` writes a `resume/generator.latex_safe_text` rendering of the posting's title/company (accent-folded; other non-ASCII dropped) *after* the no-invention validation has run on the faithful text. `tests/test_tailoring.py` guards both the decode and a real-engine non-ASCII compile.
- **Core invariant:** generated resumes never contain a fact absent from the profile. Enforced by `jobpilot/facts.py` (`FactValidator`); `jobpilot/resume/generator.py` raises `ContentInvariantError` on violation. Any change to tailoring must keep the no-invention tests green.
- **Guardrails live in `jobpilot/applying/applier.py`** and `jobpilot/store.py`; read the module docstrings before changing apply logic. Dedupe relies on recording an attempt before submitting.
- **Scoring rubric (`jobpilot/matching.py`) is a safety boundary, not a ranking nicety.** `strong` is the auto-apply band and requires both `score >= match.strong_threshold` *and* `role_relevance >= match.strong_min_role_relevance` (a low-relevance posting is capped to `shortlist` with a reason). Role relevance counts title hits (`TITLE_HIT_WEIGHT`) far above body hits (capped below the floor) and is computed over the role section only - `_role_description` drops company boilerplate above the first role heading. Retarget a search through config (`[match.target_terms]` + the floor), never by hardcoding. Keep `tests/test_matching.py` green.
- **Parseability keyword survival uses profile-present surface forms**, not canonical labels: `pipeline._run_parseability` calls `lexicon.present_surface_forms`, because the never-invent generator can only emit aliases the profile actually contains (e.g. canonical `Communication` supported via `cross-functional`). Checking the canonical label false-fails a parseable resume; don't revert it.
- **Review detail vs category (`jobpilot/store.py`):** `applications.review_reason` holds the detailed human-readable reason; `applications.review_category` holds the guard category. `TRANSIENT_REVIEW_REASONS`, `submitted_or_attempted`, and `decide_review` must read the category, never the detail, or transient-route/dedupe behaviour breaks.
- **Safe verification:** use `--dry-run` (and `examples/demo.config.toml` for a fully offline run). Never perform a real application during development.
- **Source taxonomy lives in `jobpilot/config.py` and the loaded config.** Automated read-only adapters are registered in `jobpilot/discovery/registry.py` and listed in `DEFAULT_DISCOVERY_SOURCES`. Manual link-out sources come from `config.link_out.sources` (defaulting to `DEFAULT_LINK_OUT_SOURCES`), so a source a user adds under `[link_out.sources.<name>]` is usable end to end: `linkout.is_manual_source(config, name)` drives both `link-out add` validation and the applier's review-only guard. Configured link-out sources must never be added to the registry or scraped. LinkedIn is the single documented exception: an optional, off-by-default read-only listing reader gated by `config.linkedin.enabled`; link-out is the default LinkedIn path and it is not a licence to scrape any other manual-only site.
- **Adapters carry each board's typed employment value but never drop on it.** `JobPosting.employment_type` carries the board's own typed field; the shared hard filter (`filtering.fulltime_check`) decides, rescuing a genuine intern tagged `FullTime` into human review. Do not add adapter-level typed-value drops or title-regex intern filters upstream. On search endpoints a server-side typed facet (e.g. Himalayas `employment_type=Intern`, The Muse `level=Internship`) may be used as a high-precision slice, but it must never be the only path by which a posting can be discovered: pair it with a broader query, merge and dedupe by source job id (`discovery.base.dedupe_postings`), and never let a secondary-query failure fail the adapter.
- **Unstop's adapter now uses the API's `searchTerm` keyword filter as a high-precision slice** alongside the generic feed (per the typed-facet rule above): the generic feed and one `searchTerm` query per `[sources.unstop].keywords` entry are merged and deduped by Unstop's own id, and each query failure is isolated and surfaced in `query_errors`. Each default keyword was verified live to return real rows. It also dedupes the rows the generic feed repeats across pages so the returned set has no repeats; every page is still fetched (gap G5). G4/G5 in `data/jobpilot-run-07/report.md`; `tests/test_source_adapters.py` guards it.
- **LinkedIn's read-only reader runs a configurable target-query list** (`[linkedin].keywords`, a list; a scalar string is coerced by `discovery.base.string_list`), pages each query (`[linkedin].max_pages` is per query, not per run), and merges/dedupes by LinkedIn job id. The request rate stays deliberately low (`requests_per_second`, default 0.2/s) and one query failing never fails the adapter. Still off by default and review-only. `tests/test_adapters.py` guards it.
- **Multi-query adapters report per-query coverage and failures** via `SourceAdapter.query_counts` and `SourceAdapter.query_errors` (both copied onto the `FetchOutcome` by `fetch_safe`); the CLI prints each query's *new* posting count under its source line and prints a failed query as `FAILED (<error>)` rather than an indistinguishable `0 new`. Use this when checking whether a widened query set actually adds coverage. An adapter raises only when it fetched no postings at all and a query error was recorded, so a partially degraded run still returns the successful postings with the failures visible.
- **LinkedIn and every manual-only source are review-only** by explicit product decision: discovered/tailored/packaged, never auto-submitted, never authenticated. The applier guard returns `linkedin_review` for LinkedIn and `manual_review` (`manual_source`, a non-transient reason) for the rest.
- **Tailored resumes are enforced to one page by dropping content, never by tightening spacing.** `profile.resume_page_limit` (default 1) plus `resume_fit_attempts` drive `pipeline._generate_and_fit`, which measures the compiled PDF with `resume/parseability.py:count_pages` (form feeds in the existing pdftotext output, no new dependency) and reduces deterministically within the bounded ladder in `_FIT_VARIANTS`: the least relevant bullets first, then whole projects. Spacing is never compressed - the style template's vertical layout is calibrated against its default list spacing, so any `itemsep`/`topsep`/section-gap reduction overlaps entry or section headings (the old `_tighten_block`/`layout_level` path was removed for exactly this). The generator must also match the template's per-project spacing: `_render_projects` emits `\vspace{-11pt}` only *between* projects, never after the last one, or the Technical Skills heading is pulled into the final bullet. A variant that no longer extracts a required section is rejected by `_readable` (section extraction is the safety-net readability proxy). Reduction only removes; the no-invention validator runs on every variant. The final `GeneratedResume.page_count`/`page_limit` is persisted as `applications`/`review_queue`.`resume_pages`/`resume_page_limit` and shown as a badge on the `present` card; a resume that still cannot fit is queued for review with the measured count and reason. `tests/test_page_fit.py` guards it (including a real-engine heading-overlap check); never make it fit by inventing, rewriting or shrinking the font.
- **`jobpilot present` is presentation-only.** It selects genuine technical/AI-ML roles from the pending review queue and renders `out/present/index.html` with each tailored PDF copied to `out/present/assets/<slug>/` (relative links; opens without a server). Selection is `jobpilot/present.py`: a role is technical when its role relevance in a `[present].technical_domains` domain reaches `min_role_relevance`; a `guarded_domains` domain (`research`) counts only when the posting also matches a `core_skills` term; non-technical `exclude_terms` are dropped outright as whole-word title phrases (so `visual design` drops but `data visualization` does not); borderline matches are shown only when nothing clears the floor. Each card's route label comes from the application row's stored `review_category`/`review_reason`, not the band alone: a strong-band posting the applier routed to review for a non-transient reason (e.g. an unconfirmed window) is review-only, never `Auto-apply eligible`. It never re-scores, invents content or submits. Retarget through `[present]`, never by hardcoding; `tests/test_present.py` is the guard.
- **The robots.txt gate is enforced before every automated fetch.** `jobpilot/robots.py` ports upstream's cautious checker (`RobotsGate`): the robots.txt is read at most once per host per run and the path verdict is computed from the cached body; longest-match wins with ties to Disallow, a Disallow for the agent (`[robots].agent`, default `jobpilot`) or `*` blocks, an empty body is allow-all, 404 is permitted, a soft-200 that is not a robots.txt or any other read failure is unconfirmed and **fails closed** (a browser-UA fallback is tried before giving up), with no override of any kind. Adapters declare `hosts` (netloc only); `discovery.registry.discover` builds one gate per run and `SourceAdapter.fetch_safe` checks it after the disabled/no-tokens guards, so a tokenless source never touches the network. Because `api.ashbyhq.com/robots.txt` returns HTTP 401 for every user agent, the Ashby source is not fetched by default; this is the intended safe behaviour, not an oversight (README has the per-source table and evidence). A new network adapter must set `hosts` or it is ungated. `tests/test_robots.py` guards the rules, caching and the fail-closed skip.
- **Deadlines are extracted, stored and surfaced, never used as a filter.** `jobpilot/deadline.py:extract_deadline` only accepts a date next to an application cue (so a bare date or the internship's start/end window is never mistaken for a deadline), `parse_iso_deadline` defensively rejects non-ISO stored values, and `deadline_status`/`is_stale` drive the labels in `jobpilot postings`/`queue list` (`[deadline]` config). The pipeline fills `postings.deadline` (COALESCE-preserved on upsert: absence is not a correction). Do not turn a deadline into a hard filter or let it perturb `window.py`'s classification.
- **Parseability folds typographic Unicode and verifies contact details.** `resume/parseability.py:normalize_text` applies NFC plus LaTeX's substitutions (curly quotes, en/em dash, no-break space) to both sides of every comparison, so a `'`/`--` keyword cannot false-fail; the raw extraction is never rewritten. `check_parseability` takes `required_contact`; `pipeline._run_parseability` passes the profile's name/email/phone/linkedin/github so a layout that swallows the header is caught. Keep the raw text for any dump.
- **Application lifecycle is deterministic and local.** On auto-submit (`applying/applier.py`) or `queue approve`, `jobpilot/archive.py` copies the exact resume/cover PDFs and `.tex` plus the posting text to `out/applications/<slug>/`, **never overwriting** an existing file, and refreshes `outcome.md`. `jobpilot/lifecycle.py` owns the vocabulary (`VALID_OUTCOMES`; open by exclusion, `FINAL_OUTCOMES` close it), `quiet_days` (most recent of last follow-up / submitted / updated), the 10-day/two-reminder follow-up rule and the 60-day stale sweep (`[lifecycle]` config). Store methods: `latest_application(s)`, `approved_stable_ids`, `set_outcome`, `record_followup`; CLI: `outcome`, `followups`, `stale`. Nothing is ever sent; follow-up text is a claim-free template. `tests/test_lifecycle.py` guards it.
- **`jobpilot upskill` is a pure tally.** `jobpilot/upskill.py:collect_gaps` aggregates `postings.missing_keywords` and `applications.gaps`, weighting each job by `(1 - score)`, skipping a job with no score or no recorded gaps, and counting a posting that became an application once (from the application record). No model, no back-filling; `tests/test_upskill.py` guards it.
